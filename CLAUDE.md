# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ABL compensation for the Philips Evnia 27M2N6500 QD-OLED in HDR Peak 1000 mode. Each frame's load is measured, the gain that cancels the panel's dimming comes from a panel model, and the frame is boosted and tonemapped under the panel peak. `README.md` explains the algorithms in detail and is the user-facing spec, so keep it in step with behavior changes. The project has these parts:

- `Shaders/EOTF_BoostMod3.1_27M2N6500.fx` is the main ReShade shader, calibrated from `abl_curve.csv` and aiming for the lowest EOTF error the panel allows. It started as a copy of 3.0, and the README documents it
- `Shaders/PanelModel_27M2N6500.fxh` is the panel model, generated by `Shaders/verify/fit_panel_model.py` from every row of `abl_curve.csv`. 3.1, the null test and DwmBoost include it
- `Shaders/EOTF_BoostMod2.0_27M2N6500.fx` is the older shader with a white-only table. It's kept as history, isn't maintained, and the README only mentions it under older versions
- `DwmBoost/` runs 3.1's scRGB path desktop-wide by hooking `dwm.exe`, and its output has to match 3.1 at its default settings
- `Shaders/ABL_NullTest.fx` is a by-eye test pattern that checks 3.1's compensation against the real panel

`Shaders/EOTF_BoostMod3.0.fx` is a separate line, the upstream v8.18.7.15 shader with local tweaks. It has its own algorithm, nothing else mirrors it, and the README doesn't cover it

`research.md` is a reading list on panel load models, the Samsung controller, timing and tonemapping. `abl_curve.csv` is the latest panel measurement, with white, gray and colored windows, and the README's `abl_curve.csv` section documents its columns and the fitted panel model

## Things that have to stay in sync

- `PanelModel_27M2N6500.fxh` is generated, so change `fit_panel_model.py` or the csv and rerun it, never the include. `fit_panel_model.py --check` fails when the include doesn't match a fresh fit or the curve's elasticity reaches 0.95
- `boost.hlsl` mirrors 3.1's compute passes and boost with 3.1's uniforms baked at their defaults. A change to 3.1's algorithm or defaults usually needs the same change there. `DwmBoost/verify/parity_check.py` renders frames through both and fails on any difference past rounding
- `DwmBoost/hook/pipeline.h` holds the histogram and tone curve geometry, which must match `boost.hlsl`, and the settle run and second counts. `parity_check.py` reads both and checks the settle time still covers the slowest ease of `boost.hlsl`'s smoothing period
- The 2.0 shader's `APL_ANCHORS` table is its own and nothing else copies it
- `DwmBoost/hook/boost_bytecode.h` is generated from `boost.hlsl` by `compile_shaders.cmd` during the CMake build. Never edit it by hand, and commit the regenerated file with any `boost.hlsl` change
- `DwmBoost/shared/ipc.h` is the contract between the tray app and the hook DLL (exported function names, init status codes, named shared objects)

## Commands

Everything builds with MSVC only, and there's no test framework. Verification is the panel model check, the EOTF check, the parity check and the two GPU renderers

Build DwmBoost (needs the Windows 10 SDK for `fxc`), from `DwmBoost/`:

```bash
cmake -S . -B build -G "Visual Studio 17 2022" -A x64
cmake --build build --config Release
```

This puts `DwmBoost.exe`, `DwmBoostHook.dll` and `RenderFrame.exe` in `build/bin/Release`

Run the parity check between the hook and 3.1, from `DwmBoost/verify/` (needs both renderers built):

```bash
python parity_check.py
```

Run the hook's GPU pipeline on a saved 16-bit PQ BT.2020 PNG (like a ReShade HDR screenshot) until the gain settles:

```bash
RenderFrame source.png boosted.png
```

Build and run a ReShade effect on a saved frame the way ReShade 6.8 runs it in a D3D11 game, from `Shaders/verify/` (CMake fetches ReShade's effect compiler and `ReShade.fxh`):

```bash
cmake -S . -B build -G "Visual Studio 17 2022" -A x64
cmake --build build --config Release
build/bin/Release/RenderEffect ../EOTF_BoostMod3.1_27M2N6500.fx hdr10 source.png out.png -D NAME=VALUE uniform=value
```

`scrgb` in place of `hdr10` runs it on an FP16 scRGB back buffer. After settling, it prints the effect's GPU time per frame

Refit the panel model or check the include against a fresh fit, and replay boosted frames through the model, from `Shaders/verify/` (needs numpy, scipy and opencv-python):

```bash
python fit_panel_model.py --check
python eotf_check.py source.png boosted.png
```

`eotf_check.py` takes 16-bit PQ PNGs and fails if a frame sends past the signal peak or its curve falls

After editing `DwmBoost/app/icon.svg`, run `python make_icons.py` in `DwmBoost/app/` (needs `resvg-py` and Pillow) to regenerate the committed `.ico` files

## DwmBoost architecture

- `app/main.cpp` is the tray host. It injects `DwmBoostHook.dll` into `dwm.exe`, calls its exports on remote threads, writes the config into shared memory, handles the hotkeys and the autostart task, and nudges a static desktop with a 1 px window so DWM keeps composing until the gain settles
- `hook/locate.cpp` finds `dwmcore.dll` internals by byte patterns pinned to Windows 11 build 26200 and later. Every pattern must match exactly once, or init refuses
- `hook/flip_disable.cpp` patches DWM to force composition while the boost is on (this disables VRR) and reverts it on disable
- `hook/present_hook.cpp` hooks present with MinHook and runs the pipeline only on the 27M2N6500. The present path reads a config mirror in atomics that a watcher thread fills, never the shared memory itself
- `hook/pipeline.cpp` runs the D3D11 passes from `boost.hlsl` (`CS_Setup`, `CS_Build`, `CS_Reduce`, `CS_Solve`, which also builds the tone curve lookup, then `VS_Boost` and `PS_Boost`) and is shared with `RenderFrame`. DWM only composes when something changes, so the gain smoothing runs on the time between runs instead of frames

The hook DLL links the static CRT (`/MT`) because it lives inside `dwm.exe`. MinHook is vendored under `third_party/` and stays untouched
